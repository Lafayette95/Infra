# Databento API Implementation Guidelines for Python

### **Project Goals**
    1. Build an automated Python data pipeline that pulls data from Databento API (STIR Futures and Options)
    2. Process and clean the data using pandas, saving it to a local parquet.
    3. Build an interactive Plotly Dash web app to display key metrics, trends, and charts.

## 1. System Architecture & Constraints
*   **Environment Configuration:** 
*   This project uses a Conda environment named `infra-env` ( which uses Python 3.12.14; Use PEP 8 styling )
*   To install packages or run scripts, NEVER use bare `python` or `pip`. ALWAYS use the explicit environment prefix paths:
    1. Run python: `/opt/homebrew/Caskroom/miniconda/base/envs/infra-env/bin/python`
    2. Install packages: `/opt/homebrew/Caskroom/miniconda/base/envs/infra-env/bin/pip install <package>`
*   **Asset Universes:**
    *   `GLBX.MDP3` (CME Globex): SOFR futures & options, €STR futures & options, US Treasury Futures.
    *   `XEUR.EOBI` (Eurex): Euro-Bund, Bobl, Schatz, BTP futures & options.
    *   `IFLL.IMPACT` (ICE Europe Financials): SONIA futures & options, UK Gilt futures.
*   **Data Level:** Level 1 (Top-of-Book / Best Bid & Offer).
*   **Target Schema:** `ohlcv-1m` (1-Minute Bars containing open, high, low, close, volume).

## 2. Mandatory Cost-Protection Rules (Strict Budget Guardrails)
*   **Rule 2.1: Implement Local Storage Caching Always**
    Before executing ANY historical API data request, the script must verify if data exists in a local `.parquet` file exists. If it exists, read it into Pandas with `pd.read_parquet()`. Never allow duplicate queries to charge the Databento wallet multiple times.
*   **Rule 2.2: Absolute Contracts Only (API + Database)**
    The API is queried ONLY by absolute contract raw symbol (`SRZ4`, `ZNH5`) via `stype_in="raw_symbol"`. NEVER pass wildcards (`SR3*`), empty symbols, spread instruments, or relative/continuous tickers (`SR3.c.0`) to the API. Only absolute tickers are saved to the database. Relative tickers (`SR3.c.0` calendar, `SR3.v.0` trailing-average-volume) are resolved locally from the contracts table (built from `definition` snapshots, outrights only: `instrument_class == "F"`) by `infra/relative`, so only the contracts actually needed are downloaded.
*   **Rule 2.3: Safe Filtering for Options Chains**
    Options chains cause a data payload explosion. To fetch options data efficiently:
    1. Query the tiny `definition` schema first to return active contract IDs text data.
    2. Filter the resulting dataframe locally in Python by strike/expiry.
    3. Query the pricing data (`ohlcv-1m` or `tbbo`) ONLY using the precise array of isolated contract IDs.

## 3. Code Architecture Guidelines
*   Modularity re-usability is SUPREME: including parent functions and child functions wrappers for more precise usage
*   Explicitely, I want
    1. Read function to first check the existing relevant parquet files. Evaluate which data is not available on disk, and only then query API (and save it down)
    2. All functions in 1. are  distinct funtions (reading/writing from file, checking missing data, reading API); API distinct code file, reading/writing parquet distinct file, dash distinct etc
    3. Code lives in ~/Repos/Infra; DataBase lives separately in ~/Database/ohlcv-1m/Futures
*   **Known edge cases that are found but not fixed immediately MUST be recorded in `TOFIX.md`** (repo root), not just mentioned in a conversation, commit message, or PR description and then lost. Each entry needs enough detail (where, why it happens, why it wasn't fixed now, options considered) that someone can pick it up later without re-deriving the analysis. Remove the entry once actually fixed, noting that in the fixing commit.
*   **Tests never reach the outside world.** `tests/conftest.py` blocks every non-loopback connection suite-wide (loopback stays open for Prefect's test server): an unstubbed fetch fails at once with "external network blocked in tests" naming the address. That means stub it, the way `conftest.py` stubs each source. Added 2026-10-02 after a suite run stalled >10 minutes; `tests/test_architecture.py` checks the guard.
*   **Dependencies point one way: nothing outside `infra/dashboard` may import from it.** The dashboard is the top layer - it may import `infra/analytics`, `infra/pipeline`, `infra/cycle`, `infra/storage`, ... but never the reverse. Anything a non-dashboard module needs (a data read, a computation) lives below the dashboard, and the dashboard calls down into it. The headless daily cycle in particular must never load Dash. Enforced by `tests/test_architecture.py`. (Scripts that exist to launch the dashboard, e.g. `scripts/run_dashboard.py`, are the only exception.)
*   **Point-in-time cutoff on every "latest value" parent function, as the DEFAULT going forward for anything new.** Any function whose job is "read the latest known X" (a price, a rate, a derived result) must accept an `as_of`/`today`-style cutoff parameter, defaulting to "no cutoff" (i.e. today/now) for live use - so the SAME function serves both live dashboard use and a historical backfill, with no separate backfill-only code path to drift out of sync. Concretely: filter the underlying read to `timestamp <= as_of` (via the storage layer's own `end` predicate, e.g. `infra.storage.parquet_store.read_partitioned(..., end=as_of + pd.Timedelta(days=1))` since `end` there is exclusive) - never just "the latest row in the whole dataset," which silently uses look-ahead (future) data the moment the function is asked about any day other than "now."
    *   **Found and fixed 2026-09-28, worked example:** an early version of WIRP's `today` parameter (`infra.pipeline.wirp.build_schedule`) only gated which FOMC meetings counted as "upcoming" - the underlying price lookups (`close_rates`/`live_rates`) had no cutoff at all, so a backfill loop silently returned the IDENTICAL answer for every single day (each call still read whichever row happened to be latest in the whole dataset). Fixed by adding an `as_of` parameter to `_latest_rates`/`close_rates`/`live_rates`, bound to `build_schedule`'s own `today` - the exact same parameter now drives both "which meetings are upcoming" and "what was the latest known price," so the two can never disagree with each other.
    *   This is also what makes `infra.pipeline.wirp.backfill_schedule` (and its CLI wrapper `scripts/backfill_wirp.py`) trivial and safe: it is *just* a loop calling `build_schedule(mode, today=day)` for every cached trading day and stacking the results - no bespoke backfill pricing logic exists or is needed, so a backfilled day is guaranteed identical to what the live dashboard would have shown on that day.

*   **Every model serves two use cases with ONE implementation (user requirement, 2026-10-03; details `infra/models/CLAUDE.md` 0a):**
    1.  **(a) Point-in-time continuous refit for a strategy - the important one.** A backtest refits on a schedule (e.g. weekly) using data up to that date only, SAVES the parameters as of each refit, and applies that frozen fit to the following period to produce fitted values / residuals / factors. Generic loop `infra.models.walk_forward.walk_forward`; fits export `params()` and rebuild with `from_params`; saved runs via `scripts/run_walk_forward.py --save` (`Database/Derived/ModelRuns`). This is the "point-in-time cutoff" rule above applied to fitting: a model's output for a day may depend only on fits made with data known by then (pinned by `tests/test_stats_models.py::test_walk_forward_is_point_in_time`).
    2.  **(b) On-demand interactive use in Dash:** choose the input series, the model, its parameters and a fit date on a page (`/models`), built from the SAME spec objects as (a), never a dashboard-only variant.
    Fit and transform stay separate methods (`fit(prepared, as_of)` vs `predict(prepared, start=, end=)`), possibly at different granularities (`prepare(raw, skip=("resample",))`), and data preparation (resample / diff / normalise) is a shared helper of every model (`infra/models/prep.py`), with any scaling fitted in `fit` and frozen.

## 4. Reading Data Schema Definitions & Structural Mapping
When interacting with Databento payloads, map to these native schemas:
*   `ohlcv-1m`: Use for bars. Key fields returned: `symbol`, `open`, `high`, `low`, `close`, `volume`. Index is `ts_event` (start time of bar). **Trade-based, not quote-based**: `open`/`high`/`low`/`close` are actual executed transaction prices (not bid/ask/mid), and `volume` is summed trade size — confirmed against Databento's own schema docs. For bid/ask instead, use `tbbo` below.
*   `tbbo`: Top of Book Best Bid/Offer (Level 1 Tick stream). Contains: `bid_price_0`, `ask_price_0`, `bid_size_0`, `ask_size_0`.
*   `definition`: Instrument metadata. Key fields: `instrument_id`, `raw_symbol`, `strike_price`, `expiration_date`.

## 5. Reading Symbology Best Practices
Stored/queried tickers are ABSOLUTE (Databento `raw_symbol`); relative tickers exist only in code:
*   **Futures roots (parent symbol `<root>.FUT`), all in `FUTURES_ROOTS` (`infra/config.py`):**
    *   STIR: `SR3` (3M SOFR), `ESR` (3M €STR), `SR1` (1M SOFR), `ZQ` (30-Day Fed Funds — `SR1`/`ZQ` are MONTHLY cycle, all 12 months, unlike everything else in this universe which is quarterly) on `GLBX.MDP3`; `SO3` (3M SONIA) on `IFLL.IMPACT`.
    *   US Treasuries (CBOT, on `GLBX.MDP3`): `ZT` (2Y), `ZF` (5Y), `ZN` (10Y), `TN` (Ultra 10Y), `ZB` (Classic Bond), `UB` (Ultra Bond).
    *   Eurex (`XEUR.EOBI`, data only from 2025-03-10): `FGBL` (Bund), `FGBM` (Bobl), `FGBS` (Schatz), `FBTP` (BTP). `GG` is NOT a valid Eurex root.
    *   ICE (`IFLL.IMPACT`, data from 2018-12-23): `R` = UK Long Gilt. `G`, `SOA` (1M SONIA) and `SON` are not used.
*   **ICE symbol quirk:** raw symbols look like `R   FMH0025!`. Each expiry also lists a non-trading `_Z` twin one day earlier, and `R` has off-cycle April/May-coded contracts; both would corrupt relative ranks, so ICE roots filter with `ticker_regex` (quarterly `H/M/U/Z` `!` contracts only).
*   **Absolute examples:** `SRZ4`, `ZNH5`, `FGBL SI 20250606 PS` (Eurex raw symbols are not CME-style: rank by definition `expiry`, never by parsing symbols). SR3's letter lags its expiry by a quarter (`SRZ4` expires 2025-03-18).
*   **Relative notation:** `<root>.<c|v>.<rank>`, e.g. `SR3.c.0`. Ranking uses the quarterly expiry cycle (SR3 serial contracts are excluded), configured per root in `infra/config.py`. `c.0` on ZN/Bund sits in an expiring, thin contract for weeks; prefer `v.0` there.
*   **`.v.N` ranks by the exchange's official daily CLEARED VOLUME** (`statistics` `CLEARED_VOLUME`, the daily store's `volume` column, section 8), averaged over the prior trading days with no look-ahead: `VOLUME_LOOKBACK_DAYS` (5), or `FuturesRoot.volume_lookback_days` (bond futures 2: a 5-day average only crosses ~4 sessions after the daily volume, leaving `v.0` in a dying contract past first notice). That's blocks, EFPs and spread legs included, so it runs 1.2-4x above summed outright 1-minute bars (ZQ, 2026-09). Changed 2026-10-01 from summed 1-minute bars: the official figure is the right one, it costs ~$0.000003/contract-day against ~$0.0009 for bars, and bars are now fetched only for the contract the ranking picks, never for the whole pool. The pool is the `N + 1 + FuturesRoot.volume_extra_candidates` nearest contracts (default `VOLUME_EXTRA_CANDIDATES = 3`; bond futures `1`, so `v.0` is one of the front two). Ranking reads `relative.VOLUME_HISTORY` of volume before the window, so the first days rank on real volume too. One implementation (`infra.pipeline.relative.volume_ranked_mapping`) serves the 1-minute series (`load_relative_futures`, the dashboard) and the daily ones (`load_relative_daily`) alike.
*   **3-Month SOFR Option Root:** `SR3.OPT` (`OQ` does not resolve - verified against the real API 2026-09-21; `SR3.OPT` returns 3,358 real option contracts, e.g. `SR3U6 C9762.5`, same convention as the futures root plus `.OPT`).

## 6. Database Architecture Rules: STIR Futures & Options (1-Min OHLCV)

## 6a. Storage & Indexing Strategy
*   **Index Structure:** Disk storage must be **completely flat**. Row indexes (`index=False`) are banned in the files.
*   **In-Memory Lifecycle:** Reconstruct MultiIndexes (`timestamp`, `ticker`) exclusively in RAM *after* data is loaded.
*   **Column Layout:** Value metrics (`open`, `high`, `low`, `close`, `volume`) must remain separate columns to ensure columnar query acceleration.

## 6b. Fixed-Point Scaling Constraints
*   **Price Transformation:** All price columns must be multiplied by `10000` and cast to `int32` before writing.
*   **Read Decoding:** Scaled columns must be divided by `10000.0` inside memory before computations occur.
*   **Target Columns:** `open`, `high`, `low`, `close`, and options `strike`.

## 6c. Data Schema Specifications

### Futures Parameter Mapping
*   `timestamp`: 64-bit Timestamp (`datetime64[ms]` or `INT64`)
*   `ticker`: String Category/Dictionary (`category` or `BYTE_ARRAY`)
*   `open`, `high`, `low`, `close`: Fixed-Point Integers (`int32` or `INT32`)
*   `volume`: Unscaled Integer (`int32` or `INT32`)
*   `open_interest`: Unscaled Integer (`int32` or `INT32`)

### Options Parameter Mapping
*   `timestamp`: 64-bit Timestamp (`datetime64[ms]` or `INT64`)
*   `underlying`: String Category matching the future contract ticker (`category`)
*   `option_type`: String Category limited to `P` or `C` (`category`)
*   `strike`: Fixed-Point Integer (`int32`)
*   `expiry`: 32-bit Integer Day Epoch (`datetime64[D]` or `INT32`)
*   `open`, `high`, `low`, `close`: Fixed-Point Integers (`int32`), fallback to `float32` only if premium drops below `0.0001`
*   `volume`, `open_interest`: Unscaled Integers (`int32`)

## 6d. File I/O & Partitioning Engine Settings
*   **Partition Columns:** `["year", "quarter"]` (calculated from the record timestamp).
*   **Partition Format:** Hive-style hierarchical file organization.
*   **Prohibited Partitions:** Never partition by `ticker`, `symbol`, or `day`.
*   **Read Optimization:** Force PyArrow dataset predicate pushdown using C++ expressions before moving bytes to Pandas.
*   **Compression Engine:** `ZSTD` (Compression Level: `5`).

## 6e. Trading-Day Semantics
*   **"Daily" means the exchange's TRADING day, not the naive UTC calendar day.** Config (per-dataset session hours, verified against the exchange, with a source URL) lives in `infra.config.TRADING_HOURS` / `TradingSession`. The pure bucketing function is `infra.trading_calendar.trading_day(index, dataset)`. Consumed by `infra.relative` (roll-day and `.v.N` volume-ranking assignment — `daily_volume`, `apply_mapping`) and `infra.processing.resample`'s `"1D"` bucket (requires `dataset`, e.g. `"GLBX.MDP3"`).
*   **CME Globex / CBOT** (`SR3`, `ESR`, and CBOT Treasuries `ZT`/`ZF`/`ZN`/`TN`/`ZB`/`UB`): session opens 17:00 CT and closes 16:00 CT the next day; the exchange's own convention labels the WHOLE session by the day it **closes** (e.g. Sunday evening's session is trade date Monday). `TradingSession.crosses_midnight = True`.
*   **Eurex** (`FGBL`/`FGBM`/`FGBS`/`FBTP`) **and ICE Futures Europe** (`SO3`/`R`) do **NOT** follow that pattern — their sessions sit entirely inside one local calendar day (Europe/Berlin and Europe/London respectively), so the trading day is simply that local date, no next-day label shift. `crosses_midnight = False`. Re-verify against `TradingSession.source` if hours change (ICE's SONIA/Gilt hours changed 2026-07-06).
*   **Fetch/coverage windows stay separate and unaffected.** The download-deduplication windows in `infra/coverage` and `infra/storage` (Rule 2.1) keep using simple UTC-day windows — that's a caching/cost concern, not a trading-day one, and must not be conflated with it.
*   **Intraday buckets (1m..4h) stay UTC-clock-aligned**, unaffected by this section — see the caveat this implies, documented in `infra/processing/resample.py` (and `TOFIX.md`).

## 7. Timezone Handling
*   **Everything is UTC except the very first step (config) and the very last (the pixels on screen).** Data on disk, everything returned by `infra/pipeline` (incl. `load_series`), all of `infra/processing` (incl. resampling quarter boundaries), `infra/relative`, `infra/storage` and `infra/api` MUST always be tz-naive UTC. NEVER localize, convert, or shift a timestamp anywhere outside `infra/dashboard`, with two exceptions, both in `infra/trading_calendar`: `trading_day` computes the trading-day LABEL (6e) and never alters a stored timestamp; `snap_instants` turns a configured local time into UTC instants (next bullet).
*   **Config may state times in LOCAL time, because that's how venues define them.** A fixing, settlement or benchmark close is set by the venue in its own wall-clock time, and that's the only form that stays right across DST: London and New York switch on different dates, so a fixed UTC offset is wrong for weeks each year. Such config always carries its IANA zone next to the time (`TradingSession.timezone`, `SwapCloseSpec.timezone`). It's converted to UTC the moment code reads it, via `infra.trading_calendar.snap_instants(days, local_time, timezone)`, and only UTC instants travel further. A local time is never stored, returned, or compared after that first step.
*   **Timezone display conversion is Dash-only.** It lives exclusively in `infra/dashboard` (e.g. `infra/dashboard/timezones.py`), as a pure, isolated conversion applied ONLY to the values handed to Plotly for rendering (x-axis ticks, hover labels). It must never mutate a DataFrame coming out of `infra/pipeline` — build a separate display index/copy, never write back to `bars`/`df`.
*   **Bucket boundaries are a data concept and stay fixed regardless of display timezone.** A `1D` bar is bucketed by the exchange trading day (6e) and a roll is assigned to a trading day the same way, no matter what timezone is selected for display; only the rendered label of an already-bucketed instant may shift. Never let a display timezone change which rows fall in the same bucket, which day a roll is assigned to, or any grouping/aggregation key. Trading-day bucketing (6e, a data concept) and display timezone (this section, a rendering concept) are orthogonal — they compose, but must never be confused: 6e decides which day a bar belongs to; this section only decides how that already-decided instant is drawn on screen.

## 8. Daily Settlement & Open Interest Pipeline
*   **Deliberately a separate pipeline from section 6's 1-min OHLCV rules**, not a variant of it: different schema (`statistics`, not `ohlcv-1m`), different cadence (once per trading day), a genuinely different code path (`infra/pipeline/daily.py`, `infra/processing/statistics.py`). It reuses the generic, dataset-agnostic primitives as-is (`infra.storage.parquet_store`, `infra.storage.coverage_store`, `infra.coverage.intervals`) — only pointed at a new root and a new coverage manifest, no new storage code.
*   **Storage roots:** `~/Database/Daily/Futures` and `~/Database/Daily/Options` (siblings of `~/Database/ohlcv-1m`, NOT nested under it), same hive `year=/quarter=` partitioning, flat, ZSTD level 5 — CLAUDE.md 6a/6d apply unchanged. Separate coverage manifests (`~/Database/Daily/_coverage/futures.parquet`, `.../options.parquet`) so gap-tracking never crosses between pipelines, or with `ohlcv-1m`'s.
*   **Scope: futures (absolute + relative tickers) and options, both supported.**
*   **Futures schema:** `timestamp` (the trading day, `infra.trading_calendar`), `ticker` (absolute contract, category on decode), `settlement_price` (nullable `Int32`, ×10000 fixed-point per Rule 6b — nullable because a day can have OI without a settlement yet, or vice versa), `open_interest` (nullable `Int32`, unscaled), `volume` (nullable `Int32`, the exchange's cleared volume; added 2026-10-01 and back-filled over every stored row the same day). Key columns: `["timestamp", "ticker"]`. Options carry no `volume`.
*   **A store can gain a column:** `parquet_store.read_partitioned` reads the union of every file's schema, so files written before the column existed read it as null instead of the column silently vanishing (pyarrow otherwise takes the first file's schema).
*   **Reads survive a concurrent writer:** writes replace files atomically, but a pyarrow dataset notes each file's size when it lists the directory, so a file rewritten between listing and reading fails as a truncated page or a bad thrift header (found 2026-10-02 while a backfill rewrote `Daily/Futures` every few seconds). `read_partitioned` then lists the store again and retries (`READ_RETRIES` = 4, short pauses); a persistent corruption still raises.
*   **Options schema:** `timestamp`, `underlying`, `option_type` (`C`/`P`), `strike` (`int32`, ×10000 — never null, comes from `definition`, not the statistic itself), `expiry` (`int32` day-epoch, matching the 1-min options schema, 6c), `settlement_price` / `open_interest` (nullable `Int32`, same reasoning as futures). Key columns: `["timestamp", "underlying", "option_type", "strike", "expiry"]`. Implements Rule 2.3 exactly as the 1-min options pipeline does: `infra.pipeline.options.load_definitions` (reused as-is, no new definitions-fetching code) → filter locally → `api.fetch_statistics_by_instrument_ids` (the isolated array only). One difference worth knowing: Databento caps a single request at 2,000 symbols (`api.MAX_SYMBOLS_PER_REQUEST`, verified empirically — a 3,358-contract SR3 chain request failed without batching), so both `fetch_statistics_by_instrument_ids` and `fetch_ohlcv_by_instrument_ids` batch internally now.
*   **`infra/pipeline/daily.py` handles futures, `infra/pipeline/daily_options.py` handles options** — mirrors the `infra/pipeline/futures.py` / `infra/pipeline/options.py` split exactly. (`daily.py` was NOT renamed to `daily_futures.py` for this symmetry, to avoid disrupting its already-shipped call sites — a minor, accepted naming asymmetry.)
*   **Source fields, verified against the real API 2026-09-21:** the `statistics` schema's `stat_type` enum (`databento_dbn.StatType`) — `SETTLEMENT_PRICE = 3`, `OPEN_INTEREST = 9`; and (2026-10-01) `CLEARED_VOLUME = 6`, whose `ts_ref` is the trading day it measures, published ~02:00 UTC the next day and again, final, ~14:00 UTC. Multiple updates can arrive per trading day (a preliminary settlement, then a final); the LAST one (by `ts_recv`) wins.
*   **Trading-day resolution is NOT simply `trading_day(ts_recv, dataset)`.** Databento's own `ts_ref` field is the exchange's reference date for a statistic and is preferred when present (`infra.processing.statistics.resolve_trading_day`, shared by both futures and options - verified against real data for both). Two verified quirks:
    1. **Open interest's `ts_ref` is the PRIOR trading day**, not the day it was published — OI published early one session actually reports the end-of-day figure as of the PREVIOUS session's close. Bucketing by `ts_recv` instead would silently misclassify it by one day (confirmed against real CME futures `SR3Z4` AND a real SR3H5 option contract: an OI update received 2025-03-12 01:50 UTC carries `ts_ref = 2025-03-11`).
    2. **`ts_ref` is null for Eurex** (always, in samples) **and sometimes for ICE** — for both, falling back to `trading_day(ts_recv, dataset)` is exact anyway, since neither venue's session crosses midnight (6e).
*   **Known residual gap (`TOFIX.md`):** when ICE's `ts_ref` is null specifically for an OPEN_INTEREST row, the `ts_recv`-based fallback can misattribute a same-value re-publish of the prior day's OI to the current day instead. Narrow (one venue, one stat type, only when `ts_ref` happens to be missing) and not yet fixed.
*   **Relative tickers (`SR3.c.0`, `SR3.v.0`) work on daily data too** (`infra/pipeline/relative_daily.py`), reusing `infra.relative`'s contract/mapping machinery and `infra.pipeline.relative`'s windows and `volume_ranked_mapping` UNCHANGED — only the data source differs (`infra.pipeline.daily` instead of `infra.pipeline.futures`). This works because a daily row's `timestamp` IS already the trading day, and `infra.trading_calendar.trading_day` is idempotent on an already-resolved trading day (verified across a full year, both DST transitions, every configured dataset). `.v.N` ranks on the same store's cleared volume (section 5), so daily relative series need no 1-minute data at all.

## 9. Risk-Neutral Density Analytics
*   **A derived analytics layer, not a data pipeline** (`infra/analytics/`): pure functions, no API calls, no new storage — reads already-fetched data via `infra.pipeline.daily_options`/`infra.pipeline.daily`. Extracted densities are computed on demand, never persisted.
*   **Methodology (Breeden-Litzenberger via butterfly spreads on a fitted smile, not raw finite differences):** `forward.py` (`implied_forward_and_discount`) fits the option chain's own put-call parity (`C - P = discount × (forward - strike)`, linear in strike) to get the forward price and discount factor — **no separate risk-free-rate curve pipeline needed**; both fall out of the chain itself, verified against real `SR3U6` data 2026-09-21 (implied forward matched the future's own settlement to 4 decimal places, fit was line-straight across ~100 strikes). `black76.py` prices/inverts implied vol (out-of-the-money side at each strike — puts below the forward, calls above — since deep in-the-money options have near-zero vega and a poorly-conditioned inversion). `smile.py` fits a cubic spline to the resulting vol-vs-strike smile (chosen over SVI for v1: simpler, no per-day nonlinear calibration, adequate given the dense real strike grids observed — 100+ strikes per SR3 quarterly expiry). `rnd.py` rebuilds a dense synthetic call-price curve from the fitted smile and applies the discrete second-difference, clips negative noise to 0, and normalizes to integrate to 1 over the **observed strike range only** (truncated support, not the true unconditional density).
*   **SR3 options are AMERICAN-exercise, not European** (verified via CME's own FAQ — "SOFR Options utilize the American Style option exercise"). Breeden-Litzenberger is derived for European options; this is a documented approximation, not an oversight. In practice the put-call-parity fit was still extremely clean on real data (CME's settlement price is model-derived, not a raw last-trade), suggesting the distortion is small for short-dated, near-the-money SR3 quarterlies — treat deep in-the-money / longer-dated tails with more skepticism than the body of the distribution.
*   **Scale note:** SR3 option strikes are quoted at exactly 100× the underlying future's own price scale (e.g. strike `9619.52` ↔ future `96.1952`) — confirmed empirically via the parity-implied forward matching the future's real settlement. `infra.analytics` works entirely in whatever scale the input chain uses (strike-axis-invariant); the returned density is "probability per unit of the input strike axis," not automatically re-scaled to the future's natural units.
*   **Practical range note:** avoid extracting a density extremely close to the option's own expiry (single-digit days) — the true distribution is genuinely a near-delta-function then (correct behavior, not a bug), but is hard to resolve usefully on a strike grid sized for the chain's normal spread. Verified stable and sensible on real `SR3U6` data across 6 consecutive trading days at T≈17 days: forward and peak strike drift smoothly day to day, density stays unimodal with a modest persistent skew, always integrates to 1, always non-negative.
*   **`grid_points`** (`extract_rnd`, default 400) controls the finite-difference resolution — far finer than real strike spacing, since it operates on the smooth *fitted* smile, not raw market prices.

## 10. Dashboard Structure (Multi-Page)
*   **One Dash app, multiple pages** (`dash.register_page`), not a separate app per concern — reuses the same server, assets, CSS and theme system; picking this over a second Dash process/port was a deliberate call (simpler to run, Dash's own built-in answer to "different view, same app").
*   **The theme control moved to a shared, persistent app shell** (`infra/dashboard/shell.py`, `build_shell` = nav links + theme toggle wrapping `dash.page_container`) — it is NOT duplicated per page. Each page's own `Output`/`Input` still reads `theme` (an `Input`, e.g. to color its own Plotly figures), but only the shell owns `Output("root", "className")`; a second callback writing the same Output would be a Dash error, and duplicating the theme control's id across pages would collide (Dash Pages shares one DOM/id-namespace across all registered pages, even though only one page's content is mounted at a time).
*   **Page modules self-register at import time** (`dash.register_page(__name__, path=..., name=..., layout=...)`), no `pages/` folder — kept flat with the rest of `infra/dashboard`, one file per concern (`infra/dashboard/layout.py` → `/` "Futures", `infra/dashboard/rnd_layout.py` → `/rnd` "Risk-Neutral Density"). `dash.register_page` requires the `Dash(use_pages=True)` instance to already exist, so `infra/dashboard/app.py`'s `create_app()` constructs the app FIRST, then imports the page modules (triggering their registration), then wires up `app.layout`/callbacks.
*   **The RND page is read-only, never fetches** — `infra/dashboard/rnd_selectors.py`/`rnd_callbacks.py` read directly from whatever's already cached under `Database/Daily/Options` (bypassing `infra.pipeline.daily_options.load_daily_options`, which needs a `definitions_day` matching an exact prior snapshot — the page's chosen valuation day usually isn't that day). Populate data via `scripts/update_daily_options.py` first. Strike/density are shown on the future's natural `/100` scale (CLAUDE.md 9's scale note), not the raw stored scale.
*   **Bug found and fixed while building this:** the stored `expiry` column is an `int32` day-epoch (CLAUDE.md 6c), not a datetime. Reading it directly with `pd.to_datetime()` silently reads the small integer as *nanoseconds* since epoch, giving a nonsense date near 1970-01-01 - `infra.processing.statistics.decode_expiry_column` is the one correct decoder (factored out of `decode_daily_options` for exactly this reason: a caller reading just the `expiry` column for a dropdown, without decoding the whole frame, still needs to decode it right). `infra/dashboard/rnd_selectors.py` uses it; a regression test (`tests/test_rnd_dashboard.py`) guards against reintroducing the bug.
*   **A third page, `infra/dashboard/wirp_{charts,layout,callbacks}.py` → `/wirp` "WIRP"**, follows the exact same read-only pattern as the RND page, reading through `infra/pipeline/wirp.py` - see section 11.

## 11. WIRP Analytics (Fed Rate-Move Probabilities)
*   **Another derived analytics layer, not a data pipeline** (`infra/analytics/wirp.py`): pure functions, no API calls, no FOMC-calendar config imported (meeting dates are passed in as plain timestamps by the caller - see `infra.pipeline.wirp`), no new storage. Reads already-fetched ZQ (30-Day Fed Funds futures) data via direct parquet reads, mirroring the RND page's read-only pattern (section 10). Computed on demand, never persisted.
*   **Fully usable outside the dashboard.** `infra/analytics/wirp.py` (pure math) and `infra/pipeline/wirp.py` (reads stored data, builds the schedule) are plain Python with no Dash dependency; the dashboard page and the daily cycle (section 12) both call into them. (`infra/pipeline/wirp.py` started life as `infra/dashboard/wirp_selectors.py` and was moved out once non-dashboard code needed it - see section 3's dependency-direction rule.) `infra.pipeline.wirp.build_schedule(mode, today=...)` is the one entry point both the live page AND a script call - see section 3's "point-in-time cutoff" convention for what makes that safe, and `infra.pipeline.wirp.backfill_schedule` / `scripts/backfill_wirp.py` for the historical-time-series use case it enables.
*   **Methodology (meeting-by-meeting, two read methods per meeting - not CME's full cross-meeting tree):** a ZQ contract's price implies the average daily Fed Funds rate for its delivery month (`100 - price`; Robertson & Thornton 1997). For each meeting, the implied post-meeting rate is read, in order of preference:
    1.  **The FLAT month right after the meeting, direct** (`infra.analytics.wirp.post_meeting_rate_from_flat_month`) - if that month has no FOMC meeting of its own, its whole-month average IS the market's expectation of the (constant) post-decision rate, no day-weighting needed. Preferred whenever available.
    2.  **Day-weighting the meeting's OWN month** (`infra.analytics.wirp.solve_post_meeting_rate`, formula and day-count convention from Geraty 2000 via Keasler & Goff, "Using Fed Funds Futures to Predict a Federal Reserve Rate Hike", *J. Economics & Finance Education* 6(2), 2007 - verified against that paper's own worked example) - a day-weighted blend of the pre-meeting rate (days 1..announcement day, inclusive) and the post-meeting rate (announcement day + 1..month end). Used only as a fallback when (1) isn't cached.

    **Why (1) is preferred, not just a tie-break:** day-weighting's implicit noise amplification factor is `days_in_month / days_after_the_meeting` - large for a meeting late in its own month. **Found via real data, 2026-09-28:** day-weighting October 2026's own month alone (meeting on the 28th of 31 days, amplification ≈10×) produced a nonsensical **+275bp** implied move from a genuinely modest underlying price difference; reading November 2026 (flat) directly gave a sane **+40bp**. This is the exact substitution Keasler & Goff themselves recommend "if the FOMC meeting is after the middle of the month" - this project applies it whenever available, not only for late-month meetings, since method (1) is strictly less noise-amplified even when both are usable. The dashboard shows which method backed each bar (hover tooltip; `schedule`'s `method` column).

    Meetings chain sequentially regardless of which method priced them: each meeting's resulting post-meeting rate becomes the next meeting's pre-meeting rate - self-consistent, **no external Fed Funds rate/EFFR feed needed**, matching section 9's forward/discount derivation philosophy.
*   **The pre-meeting anchor** for the *first* meeting in view comes from the nearest FLAT (no-meeting) month's own ZQ contract - its price directly gives the prevailing rate with no day-weighting needed, since nothing changes mid-flat-month (`infra.pipeline.wirp.find_anchor`, walks backward). A month that itself had a meeting is never used as an anchor, even read long after the fact - its contract price is itself a day-weighted blend, not a flat rate.
*   **Probability decomposition assumes the Fed only moves in whole 25bp steps** (CME's own FedWatch methodology states the same assumption). A meeting's continuous implied change is decomposed into the two nearest 25bp levels, weighted so the probability-weighted average change matches the market-implied value exactly (`infra.analytics.wirp.level_probabilities`) - e.g. +32.5bp implied reads as "70% chance of +25bp, 30% chance of +50bp".
*   **This is a per-meeting MARGINAL decomposition, not CME's full joint probability tree** - CME's FedWatch builds a cross-meeting tree enforcing one consistent joint path (probabilities at each node sum to 100%, the implied rate at each node consistent with every contract price at once); this implementation instead solves each meeting's own implied change independently, chained only through the single pre/post rate handoff described above. **Where this does and doesn't bite, checked against real CME FedWatch numbers 2026-09-25:** the NEAREST upcoming meeting is effectively bootstrapped from the front of the curve either way (its node depends on little beyond the current rate and the one contract right after it), so a proper tree and this sequential method should - and did - land close together: back-solving FedWatch's own published probability against our number showed a ~0.2bp gap in the underlying implied rate change, consistent with an ordinary small price-snapshot difference (a different settlement/quote capture moment), not a structural one. The joint-tree effect is expected to matter more for LATER meetings in the chain, where a single month's contract price is itself a blend of multiple compounding paths that only a true joint solve fully disentangles - and it's *always* the right model for genuinely joint questions this implementation doesn't attempt at all (e.g. "probability of at least 50bp of total cuts by year-end", which needs the full path distribution, not a per-meeting marginal one - out of scope for v1).
*   **FOMC meeting schedule** (`infra.config.FOMC_MEETINGS`): 2018-2027, verified against `https://www.federalreserve.gov/monetarypolicy/fomccalendars.htm` (2021-2027) and `.../fomchistorical{2018,2019,2020}.htm`, 2026-10-02 (2025-2026 first 2026-09-28). `end_date` is the announcement day. `scheduled=False` marks the two unscheduled 2020 cuts (announced 2020-03-03 and Sunday 2020-03-15, which replaced the cancelled March 17-18 meeting); a point-in-time user counts them only once announced (`infra.pipeline.financing.change_dates`). Extending the list back from 2025 changed no stored WIRP value (recomputed 2025-09-26..2026-10-01, identical); adding 2027 lets WIRP price the 2027 meetings the ZQ strip reaches. A 2025-08-22 "notation vote only" date is deliberately excluded (not a live 2-day meeting/rate decision) - treating it as a regular meeting would corrupt August 2025's month-to-meeting mapping. The Fed publishes next year's calendar around July of the prior year; re-verify and extend this list then.
*   **LIVE vs CLOSE toggle, reading from the two pipelines already built for this project:** CLOSE reads the latest cached OFFICIAL SETTLEMENT price from `Database/Daily/Futures` (section 8's daily pipeline); LIVE reads the latest cached 1-MINUTE bar close from `Database/ohlcv-1m/Futures` (section 6's pipeline). **"Live" is not a real-time feed** - this project only ever calls Databento's Historical API, so LIVE means the freshest 1-minute bar already on disk, not a live market print; the dashboard always shows the "as of" timestamp of whichever price it used, both modes.
*   **The toggle only ever affects genuinely UPCOMING meetings, never the anchor or an already-past meeting used to chain the rate forward.** The anchor and any past meeting in the chain (e.g. September, above) represent KNOWN, settled fact - there's no reason to prefer a noisier intraday tick over the official settlement for something that's supposed to be a solid reference point, and CME's settlement price exists precisely to be that authoritative daily figure. So `infra.pipeline.wirp.build_schedule` always sources the anchor and any past-chain month from `close_rates`, regardless of `mode`; only the upcoming meetings' own months (and the flat reference months used to price them, e.g. November backing October) follow the LIVE/CLOSE toggle - those genuinely are live-evolving forecasts a viewer might want to watch move intraday. In CLOSE mode this is a no-op (both sources are the same function); in LIVE mode it means the anchor/past-chain never need their own intraday backfill at all - only the upcoming months' contracts do.
*   **Contract-to-meeting-month mapping is by real `expiry` date** from the contracts table (`infra.pipeline.contracts`), never by parsing the ticker's month code - the same symbology caution as section 5 (Eurex raw symbols aren't even CME-style).
*   **Dashboard page** (`infra/dashboard/wirp_{charts,layout,callbacks}.py` over `infra/pipeline/wirp.py`, `/wirp`): a stacked probability bar per upcoming FOMC meeting, one segment per discrete outcome level. Read-only, mirrors the RND page's structure exactly (section 10) - never fetches; populate ZQ data first via `scripts/update_futures.py` (LIVE) and `scripts/update_daily.py` (CLOSE).

## 12. Daily Cycle (`infra/cycle`)
*   **One ordered set of steps, run over `(start, end)` (inclusive days), each followed by its own regression checks:** `ref` (0 `infra.cycle.ref.backfill_daily_ref` = Treasury auctions, CME conversion-factor files, then rebuild the Treasury reference stores, section 18; first since 2026-10-02, and `px` runs after it WITHOUT depending on it, so a reference failure never blocks the settlements) → `px` (1a `backfill_daily_px_data` = futures settlement/OI via `backfill_daily_futures_px` + cash-bond par yields via `infra.cycle.px_bonds.backfill_daily_bond_px`, section 13, + Treasury prices per CUSIP via `infra.cycle.px_treasuries.backfill_daily_treasury_px`, section 18, + repo rates and the NY Fed's securities lending via `infra.cycle.px_repo.backfill_daily_repo_px`, section 19) → `raw` (1b `backfill_daily_raw_data`, non-price inputs - macro-release vintages, section 14a, full-granularity inflation snapshots, section 15, DTCC swap-trade reports, section 16, and weekly positioning / dealer balance sheets, section 24) → `derived` (2 `backfill_daily_derived`) → `bmk_risk` → `bmk_pnl` (3 `backfill_daily_bmk` = `backfill_daily_risk` then `backfill_daily_pnl`) → `backup` (5, the vintage). Plain Python (`infra.cycle.runner`); the scheduler only wraps it, so every step and check is testable without it. Each `backfill_daily_*` function is also usable standalone from a script.
*   **Two entry points, same steps:** `run_daily_cycle(start, end)` for history backfills (`force_refetch=False`, Rule 2.1 as usual) and `run_scheduled_daily(today)` for the scheduler - each step over `[T - N business days, T]` with `force_refetch=True`. N is the step's own `revision_window_days` (global default `DEFAULT_REVISION_WINDOW_DAYS = 3`, overridable per step or per run).
*   **`force_refetch` is the ONE deliberate exception to Rule 2.1** (`infra.pipeline.daily.plan_daily_update`, default `False` everywhere): it ignores the coverage manifest and re-queries the window, because a revision of an already-published settlement can never be seen otherwise - a covered day is never re-requested. Only the scheduled run's short trailing window turns it on. `tests/test_cycle.py::test_without_force_refetch_a_revision_is_never_even_seen` pins this down.
*   **Universe (`infra.cycle.universe`, config `DAILY_BACKFILL`):** per enabled root, the `n_contracts` nearest unexpired contracts on its expiry cycle, evaluated PER DAY (point-in-time, rolls as contracts expire). Implemented as relative ranks `c.0..c.N-1` through the existing `needed_contract_windows`/`calendar_mapping` - no second ranking rule. ZQ/SR1 12, SR3 21, ESR 6, bond futures 2; ICE (`SO3`, `R`) disabled for now (~99% of daily-cycle API cost). Definition snapshots are aligned to a fixed 30-day grid (`snapshot_grid_floor`) so the daily-moving window doesn't pull a paid snapshot per root per day.
*   **Checks** (`infra.cycle.core.Check`), severity `fail` (default: step fails, every dependent step is skipped, the run reports failure) / `warn` / `info` (logged, run continues). A check that raises counts as failed, never passed. Per step: (a) today's data present, (b) no revisions, (c) custom. **`px_outliers` detects BAD PRINTS, not big market days** (`infra.cycle.px.peer_outliers`): each move in units of its own contract's typical move (z), compared with its peers' z the same day (4 nearest same-root contracts by expiry; roots too thin for that - bond futures carry 2 - use the whole same-currency bond complex). Flagged only if it moved a lot by its own standard (|z| >= 5), was out of line with its peers (|dev| >= 6), AND that deviation reversed at the next session. Calibrated on a year of real settlements (19,324 contract-days): flags exactly ESRM7+ESRU7 on 2026-09-11 and ESRZ6 on 2025-10-31 - genuine bad prints, each a kink mid-strip gone next session - and none of NFP 2025-08-01, the ECB-dated EUR days, 2026-04-08 or FOMC 2026-06-17/07-29. An earlier rule (>10x the contract's own median move) failed every one of those macro days and couldn't separate them from the prints; every clause of the new rule is load-bearing (see the constants' comment). Cost: a print is only judged once its next session exists - the latest day's candidates show as the `warn`-level `px_outliers_pending`, and are treated one day later if they reverse. **Two extensions for futures (`infra.config.BAD_PRINT_RULES`, each switchable; added 2026-10-02):** (1) a MARKET FACTOR - both thresholds are multiplied by the day's median |z| across the OTHER curves of the same currency (USD STIR judged against the Treasury futures, EUR against the Bund complex), floored at 1 so a quiet day is judged as before, and unused with fewer than 3 such instruments (`market_factor`; the flag's detail shows `market xK`). Other curves, not the contract's own: two bad prints among ESR's 6 contracts inflated their own curve's median enough to excuse themselves. Not VIX: it fell 7 points on 2020-03-10. (2) POLICY-DAY EXEMPTIONS - on each FOMC decision's first settlement (incl. unscheduled, `FOMC_MEETINGS`), ZQ/SR1/SR3 candidates are logged, never treated: the front contract reprices alone by design (2020-03-03: Treasuries moved only 2.4x normal). Registry `infra.cycle.bad_prints.EXEMPTION_EVENTS` (an ECB-days source would protect ESR the same way). Cash bonds keep the base rule. **Recalibrated over 2015-2026 (~75k contract-days, every enabled root, the cycle's own universes):** the base rule flagged 8 prints, the extended rule exactly the 3 known bad prints (unchanged, factor 1.0); the 5 dropped were genuine shock-day moves on SR1 (2020-03-03 exempt; 2020-03-09/10 and 2022-02-10 scaled), no new flag appeared. **A confirmed bad print is TREATED, not failed** (`px_outliers` is `warn`, listing each treatment) - see the bad-print policy below. Peers and ranks are ordered by the contract's real `expiry` (`UniverseMember.expiry`, from the contracts table): an earlier version ordered by the member's last day in the window, which is identical for every live contract on a short window, so on the scheduled run's 3-day window peers were effectively arbitrary.
*   **Vintages and the no-revision check (b):** the `backup` step, last and only if every other step was ok, copies the whole database (minus `_vintages`) to `~/Database/_vintages/<run day>/`, dated by the day the RUN happened. Each file is an APFS copy-on-write CLONE (`infra.cycle.vintage.clone_file`: instant, free on disk until the live file changes, and unlike a hard link unaffected by an in-place write; plain copy off APFS). Only the newest `VINTAGES_KEPT = 2` are kept (`vintage.prune`, after each backup; user decision 2026-09-30) - today's and the one the next run compares against. Each run's `*_no_revisions` checks (`infra.cycle.checks.revision_check`) compare every key the latest EARLIER vintage holds in the step's window against the live store: any value that differs is a revision - including a value FILLING a gap (NaN -> value, e.g. open interest published a session later) - and so is a deleted row; keys only in the live store are new history, not revisions. Each revision is classified (`kind`: `filled` / `changed` / `retracted` / `row deleted`) and the check's message counts them by kind. **Revisions are EXCEPTIONS, not failures** (user decision 2026-09-29): `revision_check` defaults to `warn` - logged with its details (the runner logs every non-passing check's first 20 rows at the matching level), the run continues and still writes its vintage. A failed day never becomes a baseline - the next run then compares against the last good vintage.
*   **`prune` flag** (`parquet_store.write_partitioned`, default `False` = append, overwriting only conflicting keys): `True` deletes the ENTIRE stored history of every ticker present in the incoming rows, across all partitions, then writes them. At the pipeline level (`infra.pipeline.daily.fetch_and_store_daily`) pruning also clears the ticker's coverage record - otherwise the manifest would claim history no longer on disk and it could never be re-fetched. Not yet plumbed into the 1-minute futures/options pipelines.
*   **Bad-print policy is per contract, set at instrument construction** (`DailyBackfillSpec.strict_ranks` / `bad_print_policy(rank)`, `infra.config.DAILY_BACKFILL`): a confirmed bad print on a contract of rank `< strict_ranks` (its rank ON that day, `infra.cycle.universe.rank_on`) is set to **NA** (strict - no value beats an invented one where the contract matters most); any other rank is **rolled** (replaced by its last good prior value - consecutive bad prints roll from the last GOOD one; no prior value falls back to NA). Initial config (user, 2026-09-29): every bond root's 1st contract NA; STIR NA on the front HALF of its universe (ZQ/SR1 6 of 12, SR3 10 of 21, ESR 3 of 6); roll for the rest. Consequences worth knowing: WIRP reads the latest settlement at or before its day, so an NA'd latest settlement falls back to the prior day's; bmk has no pnl row for an NA day, and the next day's pnl spans both days' moves.
*   **The adjustments log - how "touched" data is recorded** (`infra.storage.adjustment_store`, root `~/Database/_adjustments`, config `ADJUSTMENTS_DIR`): a SIDECAR store, one row per touched value keyed `(store, timestamp, key, column)`, with `action` (`NA`/`roll`), `original`, `adjusted`, `source` (the process, e.g. `px_bad_print`), `detail` and `run_day`. Chosen over a flag column on each store: raw stores stay exactly what the vendor delivered (a re-fetch can never silently undo a treatment, and revision checks keep comparing real vendor data); the log holds what a sparse flag couldn't (original value, why, which process, when) identically for every store (options and intraday later) with no schema change to any of them; and it costs nothing where nothing was touched. **Readers overlay it at read time**: `infra.pipeline.daily.read_daily_from_disk(adjusted=True)` (default) and `infra.pipeline.wirp.close_rates` apply it, so derived and bmk see cleaned data; the px checks read `adjusted=False` - bad-print detection must judge the vendor's numbers, not its own earlier verdicts. A process re-evaluating a window first `clear`s its own adjustments there, so a print later corrected upstream is no longer adjusted. `tests/conftest.py` points both readers at an empty temp log, so tests never see the real one.
*   **Daily statistics writes COALESCE, never replace a whole row** (`parquet_store.write_partitioned(..., coalesce=True)`, used by the daily futures and options stores): each row is a pivot of independently-published statistics - open interest for day X-1 only arrives in session X (section 8) - so a partial incoming row is a partial observation, not a retraction; a missing incoming value never erases a stored one. **Found and fixed 2026-09-29:** with whole-row upserts, any fetch window starting on X produced an OI-only row for X-1 that REPLACED the stored complete row, wiping X-1's settlement - every scheduled run lost the day before its window (61 GLBX settlements on 2026-09-23), as did every backfill-window boundary (63 on 2025-09-26); both repaired by a targeted re-fetch ($0.0005). The same mechanism leaves an OI-only row on each contract's FIRST stored day (the day before its window started, whose settlement was never requested) - harmless, expected.
*   **Derived metrics are PERSISTED** (`infra.cycle.derived`, stores under `~/Database/Derived/`) - unlike the dashboard's on-demand views, because the revision check needs yesterday's values on disk. Registry `DERIVED_METRICS`: each entry is a compute function + store + keys + custom checks; the presence (a) and revision (b) checks are generated from it. WIRP (CLOSE/settlement only) is the first: the stored rows ARE `infra.pipeline.wirp.build_schedule`'s output as of each day - no second implementation. Each recomputed day REPLACES that day's rows (prune on `timestamp`), never upserts, or a meeting whose outcome levels shrink would keep a stale row and its probabilities would stop summing to 1. Custom WIRP checks: probabilities in [0,1] summing to 1 per meeting; no implied move beyond ±100bp for one meeting (the class of the old +275bp bug). A day with settlements but no WIRP (typically a missing anchor month - a history backfill needs px data from ~3 months before its first derived day) fails `wirp_present` with the reason.
*   **bmk (`infra.cycle.bmk`, stores `~/Database/Bmk/Risk` and `.../Pnl`, local computation only):** `backfill_daily_risk(risk="DV01")` - one model per risk name (`RISK_MODELS`; `carry` is a recognised, deliberately-unimplemented name). STIR DV01 is exact: price = 100 - rate, so DV01 = `point_value` x 0.01. **US Treasury futures DV01 (since 2026-10-02) = the DETERMINISTIC cheapest-to-deliver's forward DV01 / its conversion factor x point value**, per day (follows CTD switches and rolls): `infra.pipeline.futures_basis.deterministic_futures_dv01`, the basis models' M0 rule (section 22) computed from the analytics + pipeline layers, since bmk may not import `infra/models`; validated against daily settlement moves (slope 0.97-1.00, R^2 >= 0.977). Module hook `bmk.BOND_FUTURES_DV01`, stubbed suite-wide in `tests/conftest.py`. Back-filled over the whole bmk history the same day (ZN ~$67/bp, ZT ~$39/bp - its $200k notional is in the point value); a day without its inputs (FedInvest END OF DAY not yet posted, no funding before 2018-05) stays NaN with the reason. Eurex bond futures still have no DV01 (no baskets or cash prices) - NaN with the reason, listed by the `warn`-level `dv01_coverage` check every run. Bond futures pnl in currency needs no CTD; pnl-per-DV01 is now real for the US roots. `backfill_daily_pnl`: `bmk` names the pnl definition (`futures_price` = settlement change x point value, per 1 long contract; cash bonds will add total-return / yield-change definitions); `pnl_per_dv01` divides by the PRIOR day's DV01 (the risk held over the day), which for STIR is just the rate move in bp. A day with no earlier settlement (first day of a history) gets no pnl row rather than a guessed one; a contract rolling INTO the universe mid-window has a few prior days fetched by px (`PRIOR_SETTLEMENT_DAYS`) so its first day still gets pnl. Both stores upsert (keys are deterministic from the universe, unlike WIRP's), because pruning whole days would also wipe roots a partial run didn't recompute.
*   **Contract point values** live on `FuturesRoot` (`point_value`, `currency` - instrument facts, not cycle config), verified 2026-09-28 against CME/Eurex contract specs (sources in `infra/config.py`). ICE left unset (disabled, unverified). Treasury futures arrive from Databento in decimal points, so the ×10000 fixed-point storage (6b) rounds e.g. 107.21875 to 107.2188 - at most $0.05/contract of pnl noise on a $1,000/pt contract.
*   **Databento availability lag is a LICENCE limitation (current plan), verified 2026-09-28 - it shapes the whole schedule, and may go away if the plan is upgraded.** On the current licence a dataset's queryable end runs BEHIND now: GLBX `statistics` exactly 8h, XEUR about a day. **On a licence upgrade:** the fetch bounding and the presence checks read the advertised end live and adapt on their own; the one hardcoded consequence to revisit is the schedule time (`infra.cycle.flows.SCHEDULE_CRON`, currently next-morning because of the 8h lag - a smaller lag would allow a same-evening run for T). Any request ending past the advertised end (`metadata.get_dataset_range`, wrapped by `infra.api.databento_client.available_end`) is rejected with a 422 - and a 422's message claiming availability "up to" a later time is NOT the queryable bound (probed: requests between the two were rejected too). Omitting `end` does NOT mean "up to available" either: Databento forward-fills `end` from `start`'s precision. So `infra.pipeline.daily.bounded_by_availability` CLAMPS any recent request to the advertised end and records coverage only up to the start of that day (a partial day is never claimed covered; a later normal run fills it in, and a range with nothing queryable yet is skipped, not covered). The presence check (a) judges each dataset on ITS latest fully-published day (`px.complete_day`), never blindly "today"; the bmk presence checks cover every settled contract-day in the window, so they stay meaningful under any lag.
*   **Scheduling (`infra/cycle/flows.py`, Prefect 3):** the only scheduler-aware module. `daily_cycle_flow` runs `run_scheduled_daily` with each step executed as its own Prefect task (`prefect_execute` - failed steps show failed in the UI; ordering/checks/halting stay in the runner, via its injectable `execute`). Schedule Tue-Sat **06:00 America/New_York** (`SCHEDULE_CRON`/`SCHEDULE_TZ`; = 10:00 UTC in EDT, 11:00 UTC in EST - local on purpose since 2026-09-30, so it never drifts against the Mac's local-time wake at a DST change; the watchdog reads the same cron in the same timezone), processing through the prior trading day: after GLBX's 8h lag has passed T-1's settlement; Eurex is judged a day older per the lag, and the T-3 re-fetch window picks each day up once it's published. `scripts/serve_daily_cycle.py` serves the schedule (needs `prefect server start` running; both are long-running processes); `scripts/run_daily_cycle.py` runs once - history backfill, `--scheduled`, `--prefect`, and a free `--dry-run` that prices every call the run would make (bounded exactly like the real fetch) without downloading anything.
*   **Missed-run watchdog** (`infra.cycle.watchdog`, `scripts/watchdog_daily_cycle.py`, launchd `com.infra.daily-cycle-watchdog`, hourly): ground truth is the VINTAGE on disk, not Prefect - no vintage dated on/after the last due cron slot (+2h grace) means the day was lost, whatever the cause (scheduler never created the run, Mac asleep, server down, run failed). Independent of Prefect so it still works when Prefect is what broke (as it did 2026-09-29: SQLAlchemy 2.1 silently crashed Prefect 3.8's scheduler - pinned `<2.1` in requirements.txt). Alerts once per missed slot via a macOS notification, with a best-effort reason from Prefect's API; state in `~/Library/Logs/infra/watchdog_state.json`. The Mac is woken for the run by `pmset repeat wakeorpoweron TWRFS 05:55:00` (local time, 5 minutes before the 06:00 New York run, all year; set by the user - `sudo`). **The wake alone doesn't keep it awake:** found 2026-10-01, with system sleep at 1 minute the Mac fell back asleep 100s after the 05:55 wake and the run only started at 06:16, on macOS's next maintenance wake. So launchd `com.infra.daily-cycle-keepawake` runs `caffeinate -i -t 600` at 05:55 Tue-Sat (a calendar job due while asleep fires on the next wake, i.e. the scheduled one), bridging to the run, which then holds the Mac awake itself. **Waking is not enough: the run also waits for the NETWORK** (`infra.cycle.network.wait_for_network`, called by both Prefect flows and `scripts/run_daily_cycle.py` before the first step): **found 2026-09-30**, the run fired on time but every request failed DNS for all 19 minutes (the Mac had woken at 04:50 and was back in a low-power dark wake - processes run, Wi-Fi isn't up; the flow's `caffeinate -i` only stops idle sleep). If any required host (Databento, Treasury, BoE, Bundesbank) doesn't resolve, it declares user activity once (`caffeinate -u`, promotes a dark wake to a full wake - the display may light briefly) and polls every 15s for up to 10 minutes, then fails with ONE clear `NetworkUnavailable` rather than dozens of per-request errors. Tests stub it out (`tests/conftest.py`). `scripts/install_launchd.sh` waits after `bootout` until the agent is really gone and retries `bootstrap` - an immediate re-bootstrap races launchd and fails with "Input/output error", leaving the agent unloaded.
*   **Known gap (`TOFIX.md`): no exchange holiday calendar.** `px_present` only judges datasets that published *something* that day; a dataset with nothing at all (holiday vs. not-yet-published) is the separate `warn`-level `px_dataset_present`.

## 13. Cash-Bond Par Yields (`infra/pipeline/bonds.py`, `infra/cycle/px_bonds.py`)
*   **Universe:** constant-maturity sovereign PAR yields, 2/3/5/7/10/20/30y, stored as absolute tickers `<country>_BOND_<tenor>y` (`US_BOND_10y`), percent. Config `infra.config.BOND_CURVES` (`BondCurve`: source, tenors, convention, `history_start`, `par_method`, `bad_print_policy`). US, UK and DE built 2026-09-30, history from 2016-01-04.
*   **Sources - free official publications, NOT Databento, one fetcher per source in `infra/api`** (network only, never touch files; each returns a long `timestamp, maturity, value` frame plus the intervals it genuinely COVERS): `treasury_client` (US Daily Treasury Par Yield Curve Rates = the CMT curve, one CSV per year, tenors read by column NAME since columns vary by year) and `boe_client` (BoE nominal gilt SPOT curve, Excel workbooks in two zips: a ~39 MB archive refreshed once a month closes, and the current month) and `bundesbank_client` (Bundesbank SDMX API: the daily SVENSSON PARAMETERS of its German Federal-securities term structure, `BBSIS.D.I.ZST.{B0,B1,B2,B3,T1,T2}.EUR.S1311.B.A604._Z.R.A.A._Z._Z.A`, 5 decimals, same-day; the same valuations under issuer `S122` are the Pfandbrief curve, not ours). Evaluated by `infra.processing.bond_curves.svensson_curve` into the model's zero curve, which the Bundesbank defines as ANNUALLY compounded (`DF = (1+r)^-T`; reading it as continuous puts par 5-8bp off). Verified 2026-09-30: ANNUAL-coupon par from the parameters reproduces the Bundesbank's own published 2-decimal par curve (item `ZAR`) on every one of 2,727 days x 7 tenors since 2016 within +-0.5bp (mean 0.00, sd 0.29 = pure rounding). **The Bundesbank API bot-challenges VPN addresses** (every request -> 303 `/.enodia/challenge`; raised as `BundesbankChallenge`, never worked around): with a VPN on at run time, DE fails `bonds_fetch_ok` that day and the gap lookback fills it in later.
*   **Par derivation is modular** (`infra.processing.bond_curves.PAR_METHODS`, chosen by `BondCurve.par_method`; user decision 2026-09-30): `None` = the source already publishes par (US); DE is derived from the Svensson parameters with `semiannual_from_annual_spot` (see the convention bullet below; `annual_from_annual_spot` is the Bunds' native annual-coupon basis - the coupon frequency is a choice the parameters leave to us, unlike a published par series); the BoE publishes spot only (plus par for just 5/10/20y), so UK par is derived for EVERY tenor by one method - `semiannual_from_spot`: `par = 2(1 - DF(T)) / sum DF(t_i)` over semi-annual coupon dates, each DF straight off the 0.5y grid. The BoE curve starts at its shortest fitted gilt (past 0.5y on ~36% of days since 2016), so coupon dates below the day's first point take that point's rate (measured cost: <=0.31bp at 2y). It does NOT yet match the BoE's own par series (up to ~4bp at 10y) - `TOFIX.md`.
*   **Storage:** `~/Database/Daily/Bonds` (hive `year=/quarter=`, flat, ZSTD 5; `par_yield` x10000 nullable `Int32`, 0.01bp), coverage `~/Database/Daily/_coverage/bonds.parquet` **keyed by CURVE** (`"US"`), since one request always returns the whole curve. Coverage is recorded only for what the source said it covers - a day not yet published is never claimed covered (Rule 2.1 still applies: covered ranges are never re-asked, though the sources are free). History on disk from 2016-01-04 (all three curves).
*   **In the daily cycle** (section 12), same checks as the futures half: `bonds_fetch_ok`, `bonds_complete` (every day a curve published has all its tenors), `bonds_fresh` (warn: latest day > `STALE_BUSINESS_DAYS` behind), `bonds_no_revisions` (warn), `bonds_sane`, and bad prints with the SAME rule as futures (`infra.cycle.bad_prints`, shared - peers = the nearest tenors on the same curve) plus one bond-only condition, `BOND_MIN_ABS_DEV` (the move must also be >= 5bp off its peers' median move in raw bp: a 2-decimal source, like the US Treasury, rounds a quiet tenor's typical move to ~1bp and inflates its z-score - found on the Bundesbank's former 2-decimal par series, where the DE 2y was falsely flagged on 2022-03-07 and 2026-03-09/10, genuine curve moves shared by the 3y/5y), treated per `BondCurve.bad_print_policy` (default `NA`) into the adjustments log under store `Daily/Bonds`. Run over all of 2016-2026, all three curves: nothing flagged; the closest calls were genuine market days that didn't reverse (SVB 2023-03-13, the 2021-02-25 auction sell-off). The scheduled run also re-plans never-covered days in the `GAP_LOOKBACK_DAYS` (30) before its window, because the BoE publishes a month's last days late (only once its archive is refreshed, after the new month's file has started).
*   **One convention for every curve: par with SEMI-ANNUAL coupons** (user decision 2026-09-30) - the US as published (the Treasury's own basis), UK (`semiannual_from_spot`) and DE (`semiannual_from_annual_spot`) derived on that basis from their zero curves. DE is therefore ~3bp BELOW the Bundesbank's own (annual-coupon, the Bunds' native basis) published par at 2026 levels - intended, not an error. Each `BondCurve.convention` states it. No bmk (DV01/pnl) for cash bonds yet.
*   **Tests never touch the network:** `tests/conftest.py` replaces `infra.pipeline.bonds.SOURCES` suite-wide; bond tests pass fake sources explicitly.

*   **Stores (all `~/Database/<schema>/Futures`, hive `year=/quarter=`, own `_coverage`, siblings of `ohlcv-1m`):** `bbo-1m` (top-of-book QUOTES sampled every minute: `timestamp, ticker, bid, ask, bid_size, ask_size`, bid/ask x10000 nullable `Int32` - one side of a thin book can be empty), and the ON-DEMAND 1-second stores `ohlcv-1s` (1-second trade bars, same layout as `ohlcv-1m`) and `bbo-1s` (1-second quotes). Every reader writes what it fetches (Rule 2.1).
*   **1-second data is for small event windows only, never fetched by a cycle.** Its readers plan the EXACT requested window (not whole UTC days, as the 1-minute stores do): paying for a whole day of 1-second data to study one hour would be waste; coverage intervals work at any resolution. A later overlapping request pays only for the uncovered part.
*   **When a row is KNOWN (point in time):** a `bbo` sample is stamped `ts_recv` on the exact minute/second and is the book AT that instant (verified 2026-09-30; its `ts_event`/`price` are the last TRADE, often much older) - known at its own timestamp. *   **Why quotes, not trades, for intraday WIRP:** ZQ deferred months trade thinly (~300 one-minute bars a day in ZQX6, 2026-09), so a "latest trade" at a grid time can be hours old and meetings would be priced from inconsistent moments. `bbo-1m` has a two-sided quote every minute whether or not anything traded. Cost 2026-09-30: `bbo-1m` ~$0.036 per ZQ contract-month; the one-month, 12-contract backfill (2026-08-31..09-29, `bbo-1m` + `ohlcv-1m` gap fill) priced at $0.67.
*   **Intraday WIRP** (`infra.pipeline.wirp.intraday_schedules`, stored `~/Database/Derived/WIRP_intraday`, 15-minute UTC grid `WIRP_INTRADAY_GRID`): `build_schedule` itself, point-in-time at each grid instant - NO second pricing implementation. Upcoming months price from the chosen intraday source (`bbo-1m` mid default; `bbo-1s`, `ohlcv-1m`, `ohlcv-1s` for ad-hoc work, e.g. `grid="1s"` over an event hour); settled months (anchor, past chain) from settlements PUBLISHED before the instant (`settlement_cutoff`: the trading day before the instant's own CME trading day, `infra.trading_calendar`). Prices are preloaded ONCE (`PanelRates`) and passed in through `build_schedule`'s `settlement_rates_fn`/`toggle_rates_fn`. Grid times with no source update in the preceding interval (weekends, the daily halt) are skipped. Each row records `price_as_of` and `oldest_price_as_of` - the STALEST upcoming-month price used, so a lagging thin quote is visible. **Known limitation (`TOFIX.md`):** meeting inclusion is day-granular, so on an FOMC decision day that meeting is treated as past all day.
*   **Ad-hoc 1-second WIRP is SAVED** to `~/Database/Derived/WIRP_1s` (`infra.pipeline.wirp.store_wirp_1s(start, end, source="bbo-1s"|"ohlcv-1s")`, read back with `read_wirp_1s`), keyed by source too - its own store, never the 15-minute one (whose backfill replaces whole days); re-running a window replaces it. Load the 1-second data first (`load_bbo_1s` / `load_ohlcv_1s`); the compute reads disk only.
*   **The intraday cycle (not yet scheduled):** `infra/cycle/intraday.py` - `backfill_intraday_px` (`bbo-1m` + `ohlcv-1m` for `INTRADAY_UNIVERSE`: all 12 nearest ZQ contracts, the daily cycle's point-in-time universe rule) and `backfill_intraday_wirp` (replaces every grid time of the recomputed days), `check_wirp_intraday` (probabilities in [0,1], summing to 1). Run by hand: `scripts/backfill_intraday.py --start --end [--dry-run] [--wirp-only]`.

## 16. DTCC Swap-Trade Archive (`infra/pipeline/dtcc.py`)
*   **What:** every swap a US person trades is publicly disseminated (CFTC Part 43). DTCC publishes one free CUMULATIVE zip per report kind per day (`pddata.dtcc.com`, no key; `RATES` is about 1 MB per weekday and holds every currency's IRS/OIS/FRA/swaption trades). It's the free source for SOFR (and thinner €STR/SONIA) swap rates and spreads; nothing extracts curves from it yet.
*   **DTCC keeps only a rolling ~2 years** (first file still published when the archive started: 2024-09-30, verified 2026-10-01). Older history is gone from DTCC, the Wayback Machine and every free mirror checked. A day not archived within that window is lost for good, so the archive is the record.
*   **Stored raw, byte-for-byte**, never parsed into the store: `~/Database/RawData/DTCC/CFTC_<KIND>/<year>/CFTC_CUMULATIVE_<KIND>_YYYY_MM_DD.zip` (config `DTCC_DIR`, `DTCC_REPORTS = ("RATES",)`). Any extraction (curves, package trades, other currencies) re-reads the zips (`read_dtcc_day`).
*   **The file on disk IS the coverage**, with no manifest. A zip is verified, then written whole (temp file + rename), so a file present means the day is archived, and an archived day is never requested again (Rule 2.1). Layers as usual: `infra/api/dtcc_client.py` (network only: 404 = no file for the day; 503 bursts retried with backoff), `infra/pipeline/dtcc.py` (plan/store/read + `load_dtcc_day`), `infra/cycle/raw_dtcc.py` (raw source `"dtcc"`), `scripts/update_dtcc.py` (manual fill, `--dry-run`).
*   **Days are DTCC's UTC days:** file D covers dissemination over UTC day D, posted once, complete, shortly after 00:00 UTC on D+1. So a New York evening (20:00-24:00 EDT) sits in file D+1: an extraction for a New York trading day must read both files.
*   **In the daily cycle:** each run requests every unarchived day in its window PLUS the `DTCC_RETENTION_DAYS` (700) before it. Checking the disk is free, so a day missed while the Mac was off is picked up by a later run long before it ages out. `force_refetch` is ignored (a published day never changes). Checks are all `warn` (a miss heals itself, so it must not cost the vintage): `dtcc_fetch_ok`, `dtcc_complete` (every day that should be published by now, over the same lookback, is on disk) and `dtcc_sane` (each new file has the columns readers rely on, `REQUIRED_COLUMNS`, and a weekday file isn't empty). Tests stub `infra.pipeline.dtcc.FETCH` (`tests/conftest.py`).
*   **Benchmark closes** are config, `infra.config.SWAP_CLOSES` (`SwapCloseSpec`): `NY1500` (CME SR3/Treasury futures settlements, 14:00 CT), `NY1530` (CMT), `NY1600` (late US close, no official counterpart) and `LDN1615` (Tradeweb FTSE gilt closing prices behind the BoE curves, and Long Gilt futures settlement). Each is a local time plus its zone (section 7), with its own windows: pure ±30 min, widened to ±60 below 3 trades; futures-adjusted ±90 min (calibrated 2026-10-01: pure accuracy is flat ±5..±60, so the window only buys coverage, 91% of snaps at ±30; adjusted error is flat ±45..±120, lowest at ±90). Every window sits inside one UTC day, so one DTCC file (asserted). Trade weights are inverse expected variance, `SWAP_CLOSE_WEIGHTING` (`SwapCloseWeighting.variance`: trade noise + drift × |Δt| + (hedge error × futures move)²). CALIBRATED 2026-10-01 on two years of USD trades (185k): noise 0.35bp, unhedged drift 2.2bp/√h over ≤30-minute gaps (the curve is concave, steep first), swap-vs-futures drift 0.22bp/√h, hedge error 0.13, all from 2.4m same-tenor trade pairs. A held-out test (3,923 snaps, prints within ±2 min as truth) shows the weights and `outlier_k` hardly move the weighted median: the windows and the upstream off-market filters do the work. The adjusted method beats the pure one by about a third (MAE 0.21 vs 0.32bp, p95 0.67 vs 1.0bp), near the truth's own noise floor. Evidence in the config comments. Products per currency: `SWAP_CURVES` (`SwapCurveSpec`: UPI FISN + underlier, spot lag, tenors).
*   **Trades** (`infra.processing.dtcc_trades`, pure): a record's own ID plus `Original Dissemination Identifier` link a trade's life. `NEWT`+`TRAD` is an execution (other `NEWT` events re-report existing risk: clearing, novation, compression), `CORR` replaces it, `EROR` cancels it, and `MODI`/`TERM` don't change the executed price. Kept: plain spot-starting par swaps on a whole-year tenor, not a package leg, not non-standard, not declared uncleared, annual fixed leg. Also dropped: **off-market coupons**, found in the first backfill (round coupons 70-170bp from the market, sometimes 8-20 prints in a cluster). Three filters: trades with an upfront fee (`Other payment amount`); platform `BILT` (bilateral: median 2.0bp off the on-platform market, 41% beyond 5bp, 7% beyond 20bp, March 2026, against 0.1-0.3bp and ~0% for every electronic platform; `SWAP_EXCLUDED_PLATFORMS`); and any print more than `SWAP_OFF_MARKET_BP` (25) from the same-tenor median within ±2h, falling back to the day's median, then to the neighbouring tenors (30bp: good prints sit up to 29.5bp from that line, so it catches garbage, not a lone print 15-20bp off - a weakness of the PURE method in thin tenors; the adjusted close and `n_trades` are the defence). After these, two years of USD closes move 4-5.5bp/day (std) at every tenor and close, and the largest moves are real event days.
*   **Closes** (`infra.processing.swap_closes` pure, `infra.pipeline.swap_closes`, store `~/Database/Derived/SwapCloses`, keys `timestamp` = the snap instant in UTC, `close`, `currency`, `tenor`, `method`): the PURE method so far. Per tenor: a weighted median of the window's prints, after dropping any print further than `outlier_k` × the larger of the window's robust spread and its own expected error, with `n_trades`, the window used, `dispersion_bp` and `se_bp`. A tenor with no print in the window gets NO row. A lone print can't reveal its own error, so filter on `n_trades`. Day D reads file D plus the corrections in files D..D+`SWAP_CORRECTION_DAYS` (10; 99% of cancellations arrive within 33 days, 95% within a day). A recomputed day replaces its rows. Reads disk only: `scripts/backfill_swap_closes.py`. Not yet in the daily cycle: it joins `derived` with the intraday scheduling (section 18, `TOFIX.md`).
*   **Futures-adjusted closes** (`method = "adjusted"`, USD only; `infra.processing.swap_hedge` pure, `infra.pipeline.swap_hedge`): each print in ±90 min is moved to the snap by ratio × (hedge mid at the snap − mid at the print), then the same estimator runs with the adjusted variance. The hedges (`SWAP_HEDGES`): 1-3y ZT, 5y ZF, 7y ZN, 10y TN, 15/20y ZB, 30y UB, each root's `.v.0` contract, with mids from `bbo-1m` (the sample stamped at or before the print). The ratio regresses daily settlement changes (same contract both days) on the matching CMT par yield over the prior 60 business days, so it's point-in-time (`SWAP_HEDGE_CMT`; R² 0.90-0.95, -58.6 ZT .. -6.0 UB bp/pt). On June 2025: 2-3x the trades, ~40% lower `se_bp`, within a few tenths of a bp of the pure close except where the pure one rests on a bad lone print. Gaps: 1-3y should hedge with the SR3 strip (needs SR3 `bbo-1m`); EUR/GBP have no stored futures quotes.

*   **Why:** financing inputs for the bond-futures cheapest-to-deliver / forward-DV01 model (general-collateral repo to delivery, and how special each deliverable is) and for total-return Treasury series. *   **Repo rates** (`Daily/Repo`, keys `timestamp` (trade day), `series`, `status`; rates x10000 nullable `Int32`, `volume_bn`; coverage `Daily/_coverage/repo.parquet` keyed per source). Caveat: `status="best"` can hand back an OFR final published ~3 months later; harmless in practice, since finals equalled the preliminaries on every day checked except a handful of `TRI` (with-Fed) days.
*   **What the data says (checked 2026-10-02, 2018-2026 unless stated):**
    *   SOFR runs ABOVE TGCR by 1.75bp on average (sd 1.5, up to 13bp on 2024-10-01): SOFR adds cleared bilateral trades, where dealers' clients pay more than money funds earn in tri-party. BGCR = TGCR within 1bp (GCF is small).
    *   OFR's DVP overnight AVERAGE runs 1.15bp BELOW SOFR. SOFR is a median that removes the cheapest trades, an average includes them, and the cheapest trades are SPECIALS. So the gap is specialness in aggregate.
    *   The Fed's own tri-party trades (its reverse repo facility, $2tn in 2022) moved the tri-party overnight average by under 1.2bp in any year: the facility rate sits where the market trades.
    *   Tri-party TERM buckets are NOT Treasury repo: `TRIV1_G30 - TRIV1_OO` is a steady 28-46bp every year, because tri-party term mixes in corporate and equity collateral. For Treasury TERM general collateral use `DVP` (almost all Treasuries): `DVP_G30 - DVP_OO` is 3-6bp in a flat-policy year and 48bp in 2022, i.e. mostly the expected policy path, which is why term GC to delivery should come from the futures curve (`TOFIX.md`).
    *   **The DTCC GCF index is not a level-consistent splice for SOFR:** over 2018-2024 it sits above SOFR by 0.3bp (2021-22, abundant reserves) to 7.7bp (2018, scarce reserves), with year-end spikes of 200bp+. A pre-2018 GC series built from it carries a regime-dependent bias of that order (`TOFIX.md`).
*   **Securities lending** (`Daily/SecLending`, keys `timestamp`, `operation_id`, `cusip`; coverage `Daily/_coverage/sec_lending.parquet`; `infra/processing/sec_lending.py`): every operation since 1999-04-29 of the NY Fed lending its own (SOMA) holdings overnight, against other Treasuries as collateral. `operation_type`: `lending` (the 12:00-12:15 New York auction: amounts submitted/accepted, `fee` = the accepted bids' weighted average in percent, SOMA holdings, `theo_available` = 90% of holdings, `actual_available` = that less loans outstanding, in whole $m) or `extension` (loans rolled, posted the next morning). `security_class`: `treasury`, or `agency`, since the program also lent the Fed's FHLB / Freddie / Fannie debt from 2009-07-09 to 2023-06-27; readers default to Treasuries. One request per year of history; the whole history (574k rows) loads in ~40s.
    *   **The fee is specialness only ABOVE the program's minimum fee**, which bids can't go below: `SEC_LENDING_MIN_FEE`, inferred from the data (96.9% of days have their lowest fee exactly on it, none below), from 150bp in 1999 to 5bp since 2009-04-08, with every pre-2008 change on an FOMC or crisis date. `excess_fee(df, schedule)` gives the signal. Only borrowed CUSIPs are listed: a bond the Fed held that nobody borrowed was not special beyond the floor (censored, not missing).
    *   **API quirks found and handled:** CUSIPs sometimes lowercase (normalised); bids on a bond the Fed doesn't hold yet (a new issue before its settlement) come with nothing accepted and fee `"N/A"` (fee NaN), a when-issued demand signal in themselves; holdings/availability were not reported before 2005-11-07 (all zeros, stored NaN).
    *   **What it shows** (2008-2026, against the OTR map, section 18): specialness is an on-the-run phenomenon. The on-the-run 10y is borrowed on 69% of days at +15.6bp over the floor on average, the 1-old 10y at +0.3bp; the on-the-run 20y is the most special (+26bp, small issues). The highest fees ever (600-680bp, 2022-2024) are bills around debt-ceiling and quarter-end episodes and on-the-run 20y bonds, above the general-collateral rate itself: borrowers paid to get the bond.
*   **In the daily cycle** (section 12, `px` step, `infra/cycle/px_repo.py`): the window plus never-covered days in `GAP_LOOKBACK_DAYS` (30) for NY Fed and lending, and `OFR_LOOKBACK_DAYS` (150) for OFR. All checks WARN, since nothing consumes these yet: `repo_fetch_ok`, `repo_fresh` (SOFR within 2 business days, OFR DVP overnight within 4, lending within 2), `repo_sane` (rates in [-1, 25]%; NY Fed percentiles ordered around the median), `sec_lending_sane` (fee at or above the minimum fee in force - a breach means the schedule is out of date - and under 25%; accepted <= submitted and <= available to its $1m rounding; every lent Treasury CUSIP in the auctions store: over all of history only 3 bonds issued before 1979-10-31, lent before 2002, fail it), `repo_no_revisions`, `sec_lending_no_revisions`. ## 20. Financing Model: the Rate to Fund a Treasury (`infra/analytics/financing.py`, `infra/pipeline/financing.py`)
*   **What:** the rate a levered client (a hedge fund in DVP repo) pays to fund a Treasury position from a start to an end date, as known at the end of `as_of`. The input to the bond-futures cheapest-to-deliver / forward-DV01 model (whose own spec comes later) and to total-return Treasury series. `financing_rate(as_of, start, end, cusip=, model="v1")` -> `FinancingQuote` (`base`, `basis`, `specialness`, `rate` = base + basis - specialness, % ACT/360). Reads disk only; pass `inputs=financing_inputs(as_of)` to reuse one day's reads across many bonds.
*   **Three swappable layers, models are named combinations** (`infra.config.FINANCING_MODELS` of `FinancingSpec(base, basis, specialness, ...)`; registries `BASE_MODELS` / `BASIS_MODELS` / `SPECIALNESS_MODELS`, each entry `fn(inputs, spec, start, end, cusip)`; `NEEDS` says what each reads, so the pipeline gathers only that). A variant = a new registry entry plus a new spec; two models evaluate side by side on the same `FinancingInputs`.
*   **v1 ASSUMPTIONS (user decisions 2026-10-02 - state them wherever v1 numbers are used):** (1) ROLLING OVERNIGHT funding, not term repo locked to the end date: the term premium (DVP 8-30 days traded a median +3.4bp over the expected overnight path, 2025-08..2026-09) is left to show up in the futures' net basis, which is wanted; (2) client basis = SOFR's 75th percentile minus its median, a rolling 20-fixing median held constant over the term (about 5-6bp in scarce-reserve years, ~0 in 2021-22); its own small year-end premium (~3bp) is left out; (3) specialness from the NY Fed lending fee, profile + decay (below); squeezes of the cheapest-to-deliver into delivery are NOT modelled.
*   **Layer 1, `sofr_futures`** (`infra/analytics/sofr_curve.py`): SOFR's overnight path fitted to the latest SR1 settlements (each settles on the ARITHMETIC average of daily SOFR over its month's CALENDAR days, a non-business day taking the previous business day's rate), FLAT between FOMC rate-change dates (announcement + 1), with fixings already published taken as known. Plus a YEAR-END TURN on each year's last business day, which futures can't separate from December's level: the median jump of the last 3 year-ends (SOFR's jump follows the reserve regime: +56bp 2018, ~0 2020-22, +9 / +16bp 2024 / 2025). Rolling overnight compounds daily. Point in time: SR1 settlements of the latest day <= `as_of`, fixings published by then (day D is out on D+1), scheduled meetings plus unscheduled ones already announced. Business days approximate SIFMA's (federal holidays + Good Friday). SR1 settlements implying a rate outside [-1, 25]% are dropped (a contract's first listing day can settle at 0.0: SR1H0 on 2019-08-16). **Checked 2026-10-02 over 2018-05..2026-09 (2,071 days):** fit residuals median 0.6bp per day, p95 4.8bp, larger only on a contract's last 1-4 unfixed days at a month- or quarter-end (the smeared spikes; max 45bp, 2019-03-28), e.g. 2025-12-31's December contract implied the year-end print at ~+19bp, actual +16, against the imposed 3bp. Ex post, rolling-overnight funding forecast within MAE 2.7bp (1 month) and 5.8bp (3 months) of realised SOFR, against 7.7 / 18.1bp for "SOFR stays where it is"; better in every year but 2021 (a tie at the zero bound), most in 2022's hikes (1 month: 2.1 vs 20.9bp); worst in 2020 (3 months 16bp, the unanticipated emergency cuts). The forecast runs slightly HIGH (+1.0 / +2.2bp): futures carry a small term premium, and the Fed cut more than priced in these years.
*   **Layer 2, `sofr_p75`:** `client_basis_bp(fixings, window)`.
*   **Layer 3, `lifecycle_decay`** (`infra/analytics/specialness.py` pure, `infra/pipeline/specialness.py` reads): a bond's specialness on day d = its LIFECYCLE profile mu(tenor, on/off-the-run rank, phase) + (today's observed - mu today) x 2^(-business days / half-life); the term value averages it over calendar days. Observed = the NY Fed lending fee above the minimum fee (section 19), par-weighted, 0 when a tracked bond wasn't borrowed (assumes the Fed held it - true for nearly every coupon issue it rolls at auction). Phase: rank 0 = share of its on-the-run life elapsed (issue date to its successor's: known once announced, else the tenor's median cycle); rank 1 = business days since its successor's issue; rank 2-5 one value each; untracked bonds have profile 0 but keep their decaying observation. Along the term the rank changes on the successor's issue date, so known events move the expectation. Profile and half-life are estimated from the 5 calendar years BEFORE `as_of`'s year (cached per year; point in time). **Estimated 2026 (from 2021-2025):** half-life 2.7 business days; 10y / 20y specialness peaks early in the on-the-run life (16 / 59bp at 10-25% elapsed) and is gone well before the next new issue (reopenings add supply); 2y / 5y peak late (14 / 10bp) and keep a short tail once 1-old (2y day 0: 17bp); 3y, 7y and 30y stay near zero. **Validated out of sample 2014-2026** (weekly, every bond within one issue of on the run, 8,445 forecasts per horizon): unbiased (-0.3bp at 1 month, +0.04bp at 3 months; "zero" is biased -2.5bp overall, -9.6bp on the on-the-run 10y), lowest RMSE of zero / today-held-flat / profile-only (1 month: 12.4 vs 14.0 / 27.7 / 12.9bp), realised moves ~0.85-0.9 per unit forecast, R2 ~0.18. Holding today's fee flat is by far the worst (RMSE double). Mean absolute error favours "zero" (specialness is usually 0 with large spikes), but carry is LINEAR in specialness, so unbiasedness is the criterion.
*   **Only matters for some contracts:** basket bonds are rarely special (2016-2026 share of bond-days > 5bp: TN 5.8% - the new 10y is deliverable into it -, TWE 2.4%, ZF 1.4%, the rest < 1%).
*   **History:** SR1 settlements from its launch, 2018-05-07 (backfilled 2026-10-02 through the cycle's own px path, 97 contracts, 20,609 rows, $0.056); before that layer 1 can't price. The backfill's bad-print pass flagged 5 SR1 prints - all genuine moves (2020-03-03 emergency cut, 2020-03-09/10, 2022-02-10 CPI); those treatments were removed, and the rule was extended so it no longer flags them (section 12).

## 22. Treasury Futures Basis (`infra/analytics/futures_basis.py`, `infra/pipeline/futures_basis.py`; sub-project `infra/models/basis`, own `CLAUDE.md`)

Methodology, the structure (pricing tiers M0 deterministic ... M3 stochastic funding & timing; add-ons T timing options, IV implied vol, MS microstructure - specialness + calendar effects, the latter read through an event-profile interface a future project-wide event study will provide; an explanatory basis-spread layer) and results: `infra/models/basis/CLAUDE.md`.

*   **Speed-ups found while building it (no output change, verified):** `infra.analytics.sofr_curve.business_days` builds its 1990-2075 calendar once and slices (rebuilding holidays per call dominated); `infra.processing.treasury_prices.coupon_dates` uses integer month arithmetic instead of `DateOffset` (identical on 12,000 random schedules).

## 23. Futures Snaps (`infra/pipeline/futures_snaps.py`, store `Derived/FuturesSnaps`)
*   **What:** per snap instant and contract, the last two-sided bbo-1m quote at or before the instant (at most `FUTURES_SNAP_TOLERANCE_MIN` = 5 min old): `bid`, `ask`, `mid`, `quote_time`, and the contract's `settlement` on that CME trading day for comparison. Keys `timestamp` (the instant, UTC), `snap`, `ticker`; prices x10000 nullable `Int32`. Every contract with bbo-1m quotes that day is snapped: each bond root's front contract from 2015 (TN from 2016), the ZQ strip where quotes exist. Pure selection `infra/processing/futures_snaps.py`.
*   **Snaps (`FUTURES_SNAPS`) are `SWAP_CLOSES`' instants by name** - NY1500, NY1530, NY1600, LDN1615 - local times converted to UTC per day (`snap_instants`), so every benchmark time lives in one place and DST is handled at that one step.
*   **`BASIS_SNAP` = NY1530, deliberately not the street's 15:00.** Street basis screens pair the futures settlement (14:00 Chicago = 15:00 New York) with 15:00 cash. Our only cash is FedInvest's END OF DAY, and it is a 15:30 snapshot (verified 2026-10-02: the CTD's daily gross-basis noise against futures at each minute, 2024-2026, is lowest exactly at 15:30 - ZN 0.49/32, ZB 1.00, UB 0.81 - against ZN 2.06, ZB 3.88, UB 4.68 at 15:00 and about the same against the settlement). Pairing it with the settlement would mismatch the two legs by half an hour (the 15:30 mid sits a median 0.75/32 from the 15:00 settlement on the bond fronts). The basis is computed at 15:30; outputs also carry the settlement and the observed option value against it, for comparison with a DLV screen.
*   **Building:** `build_futures_snaps(start, end)` (a month of quotes at a time, a rebuilt range replaces its days; all of 2015-2026 in under a minute), `read_futures_snaps(start, end, snap=, tickers=)`. Built by hand for now (`build_futures_snaps`); it joins the daily cycle's `derived` step with the intraday scheduling, like the swap closes (section 18, `TOFIX.md`). A snap is known at its own instant (point in time).

## 24. Positioning and Dealer Balance Sheets (`infra/pipeline/cftc_tff.py`, `infra/pipeline/primary_dealer.py`)
*   **Why:** inputs for the basis models' explanatory spread layer (who holds the basis trade - leveraged funds short futures against asset managers long; whether dealers have balance sheet to intermediate it), and generally useful positioning / funding-market data. Both free, keyless, weekly; added 2026-10-02.
*   **CFTC Traders in Financial Futures (TFF)** - `infra/api/cftc_client.py` (Socrata `publicreporting.cftc.gov`, network only), `infra/processing/cftc_tff.py` (pure), store `~/Database/RawData/CFTC_TFF` (keys `timestamp` = the TUESDAY the positions are as of, `report` = `futures` / `combined` (futures + options), `market_code` = CFTC contract market code, e.g. `043602` 10y note; every numeric field kept - counts `Int64`, `pct_*` / `conc_*` float, typed by NAME so every file has the same schema). Every financial market (147), from 2006-06-13, ~47k rows per report. `known_from` = the scheduled release, Friday 15:30 New York (`CFTC_TFF_RELEASE`; matched the source's `Last-Modified` to the second, 2026-10-02). Rule 2.1: a report is requested only when the source's `Last-Modified` moved past the one in `RawData/_coverage/cftc_tff.parquet`; then the last `CFTC_TFF_REFETCH_WEEKS` (8) are re-read for revisions (whole history on the first run). Accounting identity (reportable + non-reportable = open interest, both sides): exact on every row except +-1 contract in CONSOLIDATED markets (S&P 500 Consolidated etc., mixed contract sizes - source rounding).
*   **NY Fed Primary Dealer Statistics (FR 2004)** - `infra.api.nyfed_client.fetch_primary_dealer_csv` (ONE CSV, every series' whole history, ~26 MB, 0.2s), `infra/processing/primary_dealer.py` (pure), store `~/Database/RawData/PrimaryDealer` (keys `timestamp` = as-of date, `series` = NY Fed key, e.g. `PDPOSGST-TOT` net Treasury positions ex TIPS; `value` $ millions, `suppressed` where the source prints `*` (confidential) -> NaN). ~2,300 series from 1998-01-28: positions, transactions, repo / reverse repo financing by collateral and term, fails. Catalog (current series break's descriptions) `RawData/_catalog/primary_dealer.parquet`. As of WEDNESDAY, released the following THURSDAY 16:15 New York (`PRIMARY_DEALER_RELEASE`, `known_from`); MBS settlement-class series carry other dates and take the first release at least 8 days later (conservative). Rule 2.1: requested only when the next week's release has passed (state `RawData/_coverage/primary_dealer.parquet`); each fetch writes only rows that are NEW or REVISED, and counts the revisions. **Series breaks** (2001, 2013, 2015, 2022, 2024 - the reporting form changed): a key's meaning can shift across one, so compare across a break with care (`TOFIX.md`).
*   **Point in time:** `read_tff(..., as_of=)` / `read_primary_dealer(..., as_of=)` keep only rows released by `as_of` (section 3's cutoff convention).
*   **In the daily cycle** (`raw` step, `infra/cycle/raw_positioning.py`, raw sources `cftc_tff` and `primary_dealer`): an ordinary day costs one tiny request (TFF's `Last-Modified`) or none. All checks `warn` (a missed week heals next run): `tff_fetch_ok`, `tff_fresh` (latest Tuesday whose release + 3 days has passed is stored - a government shutdown delays CFTC releases and will show here), `tff_sane` (the identity above, latest week, 1-contract tolerance), `primary_dealer_fetch_ok` (with the revision count), `primary_dealer_fresh`, `primary_dealer_sane` (net Treasury positions present). Tests stub the four network hooks (`tests/conftest.py`).
